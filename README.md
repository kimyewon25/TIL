## ***SUBJECT 01. 데이터 모델링의 이해***

### 01. 데이터 모델링의 개념 및 특징

**1. 데이터 모델링의 개념**
  - 복잡한 현실세계를 추상화, 단순화, 명확화하여 중요한 요소와 관계를 일정한 표기법에 의해 표현하는 것
    
**2. 데이터 모델링의 특징**
  - 추상화(=모형화) : 복잡한 데이터에서 핵심만 표현
  - 단순화 : 쉽게 이해할 수 있는 구조로 표현
  - 명확화 : 데이터 구조, 관계를 분명히 표현

**3. 모델링이 잘못 수행될 경우**
  - 중복성 : 같은 데이터가 여러 곳에 저장 -> 비효율, 불일치 발생
  - 비유연성 : 변화에 대응 불가 -> 시스템 확장, 수정 어려움
  - 비일관성 : 동일 데이터가 다르게 저장 -> 신뢰성 저하

### 02. 데이터 모델링의 관점
  - 데이터 관점 what : 데이터 자체에 초점을 맞춤
      - 아이디, 학번, 비밀번호...
  - 프로세스 관점 how : 데이터 처리 절차와 흐름에 초점을 맞춤
      - 아이디/비번 입력 -> 과목 선택 -> 승인 -> 수강 정보 저장
  - 데이터와 프로세스의 상관 관점 interaction : 데이터와 프로세스가 상호 의존 관계에 있음을 강조,
                                             데이터는 프로세스를 통해 의미를 얻고, 프로세스는 데이터를 기반으로 실행됨
### 03. 데이터 모델링의 3단계
  - 개념적 데이터 모델링 : 현실 데이터를 추상화하여 개념적 구조 설계, 추상화 수준이 가장 높고 업무 중심적인 포괄적 모델링
  - 논리적 데이터 모델링 : 개념적 구조를 기반으로 논리적 구조 설계
  - 물리적 데이터 모델링 : 논리적 구조를 기반으로 컴퓨터에서 데이터를 저장할 구체적 방식, 즉 물리적 구조 설계, 추상화 수준이 가장 낮음

### 04. 데이터베이스의 3단계 구조
  - 외부 스키마 : 응용 프로그램이나 사용자 관점에서 데이터를 표현
  - 개념 스키마 : 외부 스키마에서 요구된 모든 데이터를 통합하여 논리적 구조 설계
  - 내부 스키마 : 개념 스키마를 실제 물리적으로 저장하는 구조

### 05. 데이터 독립성
  - 논리적 데이터 독립성
      - 논리적 사상(외부적/개념적 사상)을 통해 논리적 독립성이 보장됨
      - 개념 스키마(논리적 구조)가 변경되어도 외부 스키마(응용 프로그램 관점의 데이터 구조)가 영향을 받지 않음
  - 물리적 데이터 독립성
      - 물리적 사상(개념적/내부적 사상)을 통해 물리적 독립성이 보장됨
      - 내부 스키마(데이터 저장 방식 및 물리적 구조)가 변경되어도 개념 스키마가 영향을 받지 않음
  
### 06. 데이터 모델링의 구성 요소
  - 엔터티 Entity : 업무에서 관리해야 할 개체 또는 대상 thing을 의미 ex. 고객, 상품, 주문...
  - 속성 Attribute : 엔터티가 가지는 특성이나 정보 ex. 고객의 이름, 연락처, 주소...
  - 관계 Relationship : 엔터티 간의 연결 또는 상호작용 ex. 고객이 주문을 한다, 상품이 주문에 포함된다...

### 07. 데이터 모델 표기법
#### IE 표기법
  1. 사각형 상단에는 엔터티의 식별자 속성(PK)을, 하단에는 일반 속성을 배치함
  2. 최소 참여 수는 타원(O) 또는 수직실선(|)으로 표현되며, 각각 0과 1을 의미함
  3. 최대 참여 수는 수직실선(|) 또는 까마귀 발(삼발)로 표현되며, 각각 1과 N(다수)을 의미함
  4. 이들 기호는 조합하여 관계의 참여 제약을 나타내며, 주요 해석은 다음과 같음

#### BARKER 표기법
  1. 식별자 속성(PK) 앞에는 # 기호를 붙여 표시함
  2. 반드시 값이 입력되어야 하는 필수 속성(NOT NULL) 앞에는 * 기호를 붙여 표시함
  3. 값이 입력되지 않아도 되는 선택 속성(NULL 허용) 앞에는 O 기호를 붙여 표시함
  4. 자식 엔터티(부모 엔터티의 기본 키를 포함하여 생성되는 엔터티) 쪽 관계선에 수직실선(|)이 있으면 식별 관계를 의미함
  5. 관계선에서 실선은 해당 엔터티의 관계 참여가 필수임을, 점선은 해당 엔터티의 관계 참여가 선택임을 의미함


### 08. ERD 작성 순서
  **1. 엔터티를 도출하고 그리기**
     - 관리해야 할 데이터를 정의하기 위해 엔터티를 식별함
     
     - 학생, 강좌, 교수 등의 엔터티 도출함
     
  **2. 엔터티를 적절히 배치하기**
     - 선이 교차하거나 꼬이지 않도록 배치함
     
     - '왼쪽 -> 오른쪽', '위 -> 아래' 순으로 읽을 수 있도록 구성함
     
  **3. 엔터티 간의 관계 설정하기**
     - 식별자 관계를 우선 설정함
     
     - CYCLE 관계(순환관계)가 발생하지 않도록 주의함
     
  **4. 관계명을 서술하기(양방향)**
     - 관계명은 현재형으로 작성하며, 지나치게 포괄적인 단어는 피함
     
     - 실제 프로젝트에서는 관계명 자체를 크게 중요하게 다루지 않는 경우도 있음
     
  **5. 관계 참여도를 표현**
     - 한 개의 엔터티와 다른 엔터티 간 참여하는 관계 수를 의미함
     
     - 1:1, 1:N, N:M 관계
     
  **6. 관계의 필수 여부 확인**
    - 필수 관계와 선택 관계를 명시함


### 09. 좋은 데이터 모델의 요건
  **1. 좋은 데이터 모델의 요건**
      - 완전성 :  업무에서 필요로 하는 모든 데이터가 데이터 모델에 정의되어야 함
  
      - 업무규칙 : 업무규칙을 반영하기 위해 필요한 데이터가 데이터 모델에 표현되어야 함
               ex. 사원에는 정규직과 임시직이 있으며, 정규직만 호봉 정보를 가짐 이라는 업무규칙을 반영하기 위해
                   데이터 모델에 사원 구분, 호봉 등의 속성이 명시되어야 함.
                   
      - 중복배제 : 동일한 사실은 반드시 한 번만 기록하여야 함
  
      - 데이터 재사용 : 회사 전체 관점에서 공통 데이터를 도출하고, 이를 전 영역에서 사용할 수 있도록 설계해야 함
  
      - 통합성 : 동일한 데이터는 조직의 전체에서 한 번만 정의되고, 이를 여러 다른 영역에서 참조, 활용해야 함


### 10. 엔터티의 분류
  **1. 물리적 형태의 존재 여부에 따른 분류**
     - 유형 엔터티 : 물리적인 형태가 있고 안정적이며 지속적으로 활용됨 ex. 교수, 강의실, 학생...
     
     - 개념 엔터티 : 물리적인 형태는 존재하지 않으나 관리해야 할 개념적 정보 ex. 수업, 보험상품...
     
     - 사건 엔터티 : 업무 수행 과정에서 발생하며 비교적 발생량이 많음(각종 통계 분석의 주요 대상이 됨) ex. 수강신청, 주문, 입금, 로그인 로그...

    
  **2. 발생 시점 및 상속 관계에 따른 분류**
     - 기본 엔터티 : 다른 엔터티로부터 영향을 받지 않고 독립적으로 생성되며, 스스로 주식별자를 갖는 엔터티 ex. 직원, 고객, 상품, 부서...
     
     - 중심 엔터티 : 기본 엔터티로부터 주식별자를 상속받아 생성되며, 주로 업무의 핵심적인 데이터를 관리하는 엔터티 ex. 급여, 주문...
     
     - 행위 엔터티 :  특정 사건이나 활동의 결과로 생성되는 데이터 
                     두 개 이상의 엔터티(중심 또는 기본 엔터티) 간 관계를 통해 데이터가 생성됨 ex. 주문 내역, 결제 기록, 수강신청 내역...


### 11. 엔터티의 특징 및 명명 원칙
  **1. 엔터티의 특징**
     - 엔터티는 해당 업무(비즈니스)에서 관리할 필요가 있는 정보를 포함해야 함
     
     - 유일한 식별자(주식별자)에 의하여 식별이 가능해야함
     
     - 영속적으로 존재하는 다수(둘 이상)의 인스턴스의 집합이어야 함
     
     - 업무 프로세스에 의하여 아용되어야 함(생성, 조회, 갱신, 삭제와 같은 CRUD 연산 중 최소 한 가지 연산에 관여해야 함)
     
     - 반드시 속성을 가져야 함
     
     - 주식별자만 존재하고 일반 속성은 없는 경우는 바람직하지 않음
     
     - 다른 엔터티와 최소 한 개 이상의 관계를 가져야 함



### 12. 관계의 개요
  **1. 관계와 페어링**
    - 관계 : 두 개 이상의 엔터티 간의 논리적 연관성
    
    - 페어링 : 엔터티 내 인스턴스 간의 개별적 연결 상태
    
    -ex. '강사'엔터티와 '수강생'엔터티는 '강의한다'라는 관계를 가짐 -> '강사1'인스턴스와 '수강생1'인스턴스가 페어링됨


  **2. 관계의 분류**
    - 존재에 의한 관계 : 존재 자체로 엔터티 간 연관성이 형성되는 관계 
            ex. '사원'과 '부서'는 존재 자체로 '소속한다'라는 관계가 형성됨
    
    - 행위에 의한 관계 : 특정 행위나 이벤트 발생으로 엔터티 간 관계성이 형성되는 관계 
            ex. '고객'이 '주문'을 하는 행위를 통해 고객 엔터티와 주문 엔터티 간 관계가 형성됨
    
    - 상호 배타적 관계 : 두 가지 이상의 선택지 중 오직 하나에만 선택될 수 있는 관계 
            ex. '사원'은 '정규직' 또는 '계약직' 중 하나의 고용형태만 가질 수 있음

### 13. 관계의 표기법
  **1. 관계명의 명명 원칙**
    - 애매하거나 의미가 모호한 동사('관계된다', '관련있다'...)는 피해야 함
    
    - 관계명은 현재형으로 표현하며, 과거 혹은 미래형 표현('~할 것이다', '~했다')을 배제함
    
    - 바람직한 관계명: '신청하다', '포함한다', '관리한다'...


  **2. 관계 차수 Degree**
    - 관계를 통해 엔터티 간 참조 가능한 인스턴스 수를 의미하며, 일반적으로 1:1, 1:N, N:M 형태가 존재하며, 대응수 Cardinality 개념과 유사함


  **3. 관계의 선택성**
    - 필수 참여 : 관계 형성 시 한쪽 엔터티 인스턴스에 대응되는 인스턴스가 반대편 엔터티에 반드시 존재해야 함
    
    - 선택 참여 : 관계 형성 시 한쪽 엔터티 인스턴스에 대응되는 인스턴스가 반대편 엔터티에 없어도 무방함

    
  **4. 관계 읽기**
    - 각 사원은 하나의 부서에 반드시 소속된다
    
    - 각 부서는 여러 사원을 선택적으로 포함한다
    
    각 / 기준 엔터티 Source / 관계차수 / 대상 엔터티 Target / 선택성 / 관계명


    
### 14. 속성의 개요
  **1. 속성의 개념**
    - 엔터티를 구성하는 가장 기본적인 정보 단위로, 엔터티의 고유한 특성과 성질을 구체화하는 요소
    
    - 엔터티의 특성 혹은 본질적 성질을 명확히 표현
    
    - 의미상 더 이상 분리되지 않는 최소의 데이터 단위
    
    - 엔터티 인스턴스의 성격을 구체화 : 엔터티에 속한 각 인스턴스 각각에 대해 구체적인 특징을 부여함
    
  **2. 엔터티, 인스턴스, 속성, 속성값 간의 대응 관계**
    - 엔터티 : 둘 이상(여러 개)의 인스턴스를 가짐
    
    - 인스턴스 : 엔터티를 구성하는 개별 데이터 행으로, 각 인스턴스는 다수의 속성을 가짐
    
    - 속성 : 엔터티가 관리해야 할 정보를 나타내며, 각 속성은 단 하나의 속성값을 가짐
    
    - 속성값 : 각 인스턴스에 대입되는 실제 데이터 값

  **3. 속성의 특징**
    - 속성은 해당 업무에서 반드시 관리해야 할 의미 있는 정보를 표현해야 함
    
    - 모든 속성은 엔터티의 주식별자에 함수적으로 종속되어야 함
    
    - 하나의 속성은 단 하나의 값을 가져야 함(원자값)

### 15. 속성의 표기
  **1. 속성의 명명 원칙**
    - 업무 현장에서 실제로 사용하는 용어를 기반으로 부여함
    
    - 약어의 사용은 가능한 한 지양함
    
    - 서술적 표현 대신 명사형을 사용하여 간결하고 명확히 표현
    
    - '~의', '~에 대한' 등의 수식어와 소유격 표현은 피함 
    
    - 가능한 한 전체 데이터 모델 내에서 유일하게 정의(권장 사함)


  **2. 속성의 표기**
    - IE 표기법에서는 엔터티를 사각형으로 표현하고, 그 사각형 내부를 가로선으로 구분하는 방식을 사용함
    
    - 엔터티 이름(과목, 강사, 사건)은 사각형 바깥쪽에 기술

    - 사각형 내부 상단 부분에는 엔터티의 식별자 속성(과목코드, 강사사번, 사건번호)을 배치

    - 하단 부분에는 일반 속성(과목명, 과목설명...)을 배치


  **3. 속성의 도메인**
    - 도메인은 각 속성이 가질 수 있는 값의 범위와 유형을 정의하는 개념

    - ex. 평점 속성 : 0.0 이상 4.5 이하의 실수형 데이터
          주소 속성 : 최대 20자 이내의 문자열


### 16. 속성의 분류
  **1. 속성의 특성에 따른 분류**
    - 기본 속성 : 업무에서 직접 도출된, 가장 일반적인 속성

    - 설계 속성 : 데이터 모델링 과정에서 필요에 의해 새로 정의된 속성, 주로 코드 형태로 추가되며, 설계 속성과 기본 속성을 명확히 구분하기는 매우 어려움

    - 파생 속성 : 다른 속성들로부터 도출된 속성, 통계용 데이터나 연산 결과가 대표적이며, 가능한 최소화 하는 것이 바람직함

  **2. 엔터티 구성 방식에 따른 분류**
    - PK 속성 : 엔터티의 각 인스턴스를 유일하게 식별할 수 있는 속성
                반드시 존재하며, 중복될 수 없음

    - FK 속성 : 다른 엔터티의 PK를 참조하는 속성
                엔터티 간 관계를 형성하며, 데이터 무결성을 유지하는데 중요

    - 일반 속성 : PK, FK를 제외한 나머지 모든 속성
                 엔터티의 특징과 정보를 나타내는 대부분의 속성이 여기에 해당


  **3. 분리 가능성에 따른 분류**
    - 복합 속성 : 하나의 속성이 의미적으로 분해 가능한 하위 속성들로 구성 ex. '주소'를 '시/도', '군/구', '상세주소'로 나늘 수 있음

    - 단순 속성 : 더 이상 분해할 수 없는 원자적 속성 ex. '성별', '연령'...


  **4. 속성값의 수에 따른 분류**
    - 다중값 속성 : 하나의 속성이 여러 값을 동시에 가질 수 있는 경우 ex. '취미', '연락처'...

    - 단일값 속성 : 하나의 속성이 하나의 값을 갖는 경우 ex. '생년월일', '학번'...
